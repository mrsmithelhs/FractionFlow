## Requirement 0 — Inventory, propose and stop

Run preflight and pin the committed baseline. Save `mechanism.md` and a coverage ledger under `reports/development/plan-85-cross-recipe-problem-bank-expansion/`. Inventory **every** currently reachable standalone practice type from the app registry. Record current count and recipes, admitted numerical and presentation bounds, data and membership owners, known usable capacity, any per-record source dependencies, and an attainable count with rationale. Report composed sessions separately because they consume existing tasks.

Propose a reproducible authoring method, duplicate rules by family, representative browser cases, disjoint assignments, and versioned publication. Account for how a larger active set affects the existing fixed Next and end-of-set behavior. Report the owner tradeoff if current navigation makes a large published set unsuitable. Keep pool size, active membership and actually reachable count separate. Stop for orchestration review before writing content or activating any membership.

## Author and integrate

1. **Target at least 30 meaningfully distinct problems per standalone type.** Use existing recipe eligibility and current representation limits. Plan for all eligible types in one wave. For each type below 30, report verified capacity or the specific blocker and the smallest follow-up. A known example is Plan 84, whose fixed whole and denominators 2, 4 and 8 allow at most 11 supplied mixed forms before even collapsing equivalent spellings. Different answer positions, IDs, copies or cosmetic spellings do not make another problem. Use task-aware duplicate rules. Preserve an existing task's meaningful operand roles and avoid counting mere commutative reversals toward the target unless the learner's work genuinely differs.
2. Use compact authored records, optionally produced from reproducible deterministic candidate enumeration. Derive exact results, admission and unique correct answers where applicable through existing code. Review coverage and plausible alternatives across the batch. Avoid both answer-position patterns and long runs of nearly identical tasks. Use stable IDs and preserve authored notation where it serves the task. Keep candidate data and coverage rules distinct from the reusable recipe validator.
3. Publish through the approved versioned membership path. Keep historical memberships, definitions and replay meanings intact. Preserve fixed ordering, fresh-attempt behavior, current session and scheduler selections, and existing progression. Verify the actual launch path reaches new items. Record any valid but unpublished content separately from live counts. Escalate families that require recipe, renderer, replay-schema or progression changes rather than expanding source scope to satisfy a quota.
