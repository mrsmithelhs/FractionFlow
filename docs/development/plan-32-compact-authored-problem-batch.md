## Goal and why this packet exists

Make additional supported problems compact data additions with shared task logic,
not separate lesson implementations or repeated agent-authored arithmetic. Plan 26
already proves multi-item navigation; Plan 30 proves offline materialization.
This packet proves production authoring and whole-episode closure across a varied
batch. One new fixture alone does not satisfy the objective.

## Non-goals and dependencies

No new family, shared-factor/nested/subtraction task, new beats, random selection,
adaptive policy, persistence, capacity expansion, framework migration, dependency
install or deployment. Preserve current task semantics and representation limits.
Plan 30 supplies accepted investigation evidence; Plan 26 supplies set lifecycle;
Plan 31 precedes source work to serialize shared UI/test evidence and establish
the accepted notation baseline. That is sequencing, not a mathematical dependency.

## Implementation requirements

### Requirement 0 — Investigate, propose and stop before source

Run preflight, record the current route/replay baseline, and propose:

1. Compact record fields, shared recipe and exact write paths. Distinguish authored
   misconception/distractor/premise-unit/answer-position policy from computed truth.
   Provide readable examples of materialized instructional outputs for owner review;
   the experimental Plan 30 hash policy is not automatically approved pedagogy.
2. A deterministic inventory under the existing relatively-prime, proper-addition
   task. Plan 30 found 18 ordered two-path candidates / nine swap classes under
   its bounds; regenerate current eligibility rather than treating that as a bank.
   Propose a varied admitted batch spanning numerator values, denominator pairs,
   operand order and scale factors. Report swapped duplicates separately. Include
   multiple new mathematical problems; neither an arbitrary quota nor one-item
   integration can substitute for demonstrated coverage. Explain each exclusion.
3. Immutable IDs/revisions for inputs, recipe, materialized task data and ordered
   set, complete eligible-unit coverage, new set order/exhaustion, and reconstruction
   of old replay envelopes. Prove reordering input enumeration does not silently
   change an item's semantic output. Recipe changes require new revisions.
4. Bounded alignment of authored-data and closure admission with actual presentation
   capability (choice count, unique forms, renderable ranges and exactly one correct
   answer). Consolidate duplicated revision discovery only as needed. Inspect current
   code before assuming Plan 30's observed gaps remain. No truth in renderers.
5. All-item/path automated completion coverage and a browser sample map tied to
   meaningful risks rather than one copied journey per record. Owner/orchestrator
   must approve instructional rules, batch membership and mechanism before source.

Stop at the gate. Do not activate experimental candidates merely because they
pass math checks. Stop on any need to widen the accepted task/capacity contract.

### Requirement 1 — Reusable authoring and admitted learner reach

Implement the approved compact batch and small shared materializer. A new record
within the approved policy must require data and validation, not per-item source
branches. Complete authored data for every admitted unit and retain truthful
premise outcomes plus three distinct renderable reflection choices with exactly
one equivalent answer. Reject duplicate mathematical distractor forms, malformed
policy/records, missing routes and out-of-capability proposals before episode start.
Keep response order/incorrect-case selection deterministic under approved policy.

Register only the approved batch through the existing practice goal and explicit
Next lifecycle. No family buttons. Preserve Retry identity, clean Next state,
support/condition/view settings, return/re-entry, explicit exhaustion and replay.
Retain task-local concise help, answer withholding and established access/motion.
No additional learner explanations or redundant headings to describe the mechanism.

### Requirement 2 — Deterministic broad coverage

Persist an auditable per-item/path manifest with IDs/revisions, operands, target
units, eligibility/admission and validated task-data outcomes. Run exact/content
and admission validation plus automated whole-episode completion for every admitted
item/path across applicable conditions and both support profiles. Include recovery,
help, reflection, reset and replay coverage; explain which checks sweep all rows
and which exercise shared transitions with representative discriminating inputs.
Avoid hand-written arithmetic or model evaluation as test oracles.

Demonstrate fail-first rejection of wrong premise truth, duplicate IDs/forms,
multiple correct answers, insufficient/out-of-range choices and missing eligible
path data. Include reorder stability and legacy replay reconstruction tests.
Report candidates, mathematical problems, swap classes, admitted paths and refusals
separately. Measure actual authoring changes/files/record size with comparison
boundaries stated; do not infer token or effort savings from abbreviated bytes.

### Requirement 3 — Discriminating mounted evidence

Use browser samples covering distinct geometry/conversion factors, the largest
admitted unit, both support profiles, both premise outcomes, visual and linear
paths, normal/reduced motion, keyboard and non-drag browser touch. Demonstrate
actual Next reach into new items and exhaustion of the approved set; injection
alone is insufficient. Check recovery/local help, Replay, dirty-state reset and
historical focus contracts. Save representative screenshots and bounds at 360px
reference sizes and a Chromebook-size viewport. Keep questions/controls usable,
report vertical scrolling honestly, and state physical-device/AT limits.
Retain legacy invariant coverage, including notation-independent answer-leakage
and new-boundary motion checks. No vacuous or weakened assertions to fit the batch.
Run normal tests/build/routes, packet lint and diff check after scoped evidence.
