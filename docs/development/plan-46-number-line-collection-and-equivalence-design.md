## Goal and reason

Turn the owner's three-fraction placement idea into ONE short reusable task:
learners place a small collection before explicit Check, connecting fraction
labels to order and, where applicable, the same numerical position. Recommend
whether equivalence recognition or ordering is the first learning emphasis; do
not introduce two full lessons or an appended reflection to cover both.

Plan39 supplies an accepted one-fraction placement interaction. It does not
establish multi-token selection, coincident fractions, recoverable collections
or representation switching. Design those responsibilities before source work.
No efficacy or engagement outcome follows from a larger number of draggable tiles.

## Requirement 1 — recommend one concise collection task

Use three fraction labels as the design starting point, not a mandated drag-only
interaction. Recommend a complete beginning, partial placement, wrong Check,
revision, acceptance and Next/final-return journey. One final Check evaluates the
collection; do not auto-accept each token or add empty Continue/Finish steps.
Explain what the learner produces and what remains supplied context.

Keep unplaced fractions visibly outside the line in a distinct starting area;
never imply midpoint placement or expose correct endpoints through aligned bars.
Specify selecting/repositioning a placed fraction, deterministic snapping, live
drop feedback, cancel/invalid-drop restoration and direct touch/non-drag controls.
Use stacked notation and concise prompts, with 44px targets and uncluttered
narrow-screen layout. Annotated wireframes are design artifacts, not rendered proof.

Include equivalent labels sharing EXACTLY one coordinate. Separate token identity
from normalized value; do not reject legitimate equality as duplicate content.
Recommend one honest co-location treatment (e.g. separated labels tethered to
the same anchor) and explain hit selection, keyboard order and linear equivalent.
Never displace mathematical points just to avoid overlapping tiles. Consider an
all-equivalent collection and explicitly include or defer it with a reason.

Specify partial/wrong feedback without auto-solving positions, unexpectedly
clearing established placements or claiming misconception diagnosis. Recommend
whether correct placements remain editable and how feedback associates with
each label. Define help, assistance provenance and More/Less consequences without
performance adaptation or rendering-owned correctness/support policy.

## Requirement 2 — exact collection/capability and lifecycle contract

Propose compact collection records with stable member IDs, original fraction
forms and one authored task purpose. Derive positions/equivalence/order through
existing exact APIs, not answer keys. Give roughly 4–6 illustrative collections
covering distinct ordering, equivalent labels plus a contrast, input orders that
do not disclose spatial order, and boundary/co-location cases. Check them through
existing math APIs; reuse algorithms rather than hand-reasoning arithmetic.

Start on [0,1]. Recommend the shared offered-position lattice and source bounds
using actual current line capability; do not assume each raw source denominator
must equal the line's partition count, or automatically extend beyond accepted
density. Identify examples rejected by capability. Larger denominators, [0,2],
mixed/improper values and random bank activation remain separate work.

Specify authoritative partial placement/selected-token state, raw intents, fixed
schedule, draft/help/focus ownership and invalidation identity. Different source
labels with equal values must remain distinct controllable members. No renderer
may determine location truth. Preserve state across access-path changes, help,
resize and remount; define exact restart/return/Next reset and replay obligations.
Recommend a bounded first source seam, not a generic multi-representation engine.

Distinguish visual/linear access switching from actual bar/line representation
switching. State what this task proves about each; if a representation-change
opportunity is recommended, name the meaningful learner connection and state to
preserve. Do not add an arbitrary switch solely to claim Roadmap35 completion.

## Requirement 3 — evidence plan and source recommendation

Recommend one first source slice, small batch bounds and an explicit branch-to-
evidence map. Separate all-record exact/mounted checks from sampled real browser
journeys at narrow/Chromebook sizes, enlarged type, keyboard, touch, reduced motion
and linear access. Include ordinary-assertion seeds for hidden auto-placement,
false separation of coincident values, lost partial state and incorrect aggregate
acceptance. No presence-only proof or seed-specific failure shortcut.

Use Plan39's repeated active-view/geometry/receipt failures as evidence for any
needed SMALL shared verifier support. Recommend a separate tooling prerequisite
only when the source slice actually needs it; do not implement/refactor tooling
here. Owner receives concrete recommended choices and limits, not a blank menu.
