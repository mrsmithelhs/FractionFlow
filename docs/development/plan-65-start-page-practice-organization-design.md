## Goal, problem and references

Each new practice type currently adds another entry button; optional record controls
add another secondary area. Do not make learners navigate an implementation catalog
to start useful practice. Recommend one calm organization that scales by mathematical
goal and keeps every currently available practice reachable, without extra copy.

Read AGENTS.md, implementer-prompt.md, decision-log.md, board, founding principles/
instruction/grammar/accessibility; Plan26 goal/registry decisions, Plan60 accepted
authored session, Plan62 presentation, Plan63 optional record and Plan64 shell proposal
or accepted contract as it exists. Trace actual registry, entry ordering/first Tab,
gear/settings, fragments, return focus, About/credit, record controls and route witnesses.
Pin current source. Plan64 may be active: its unapproved choices are assumptions,
not product facts. Coordinate through orchestration; do not redefine its exit policy.

## Required design

Compare compact organizations with a clear default practice path and a secondary
“Choose what to practice” path grouped by learner goals, not denominator families,
plan IDs, renderer types or reviewer taxonomy. Recommend one. State the exact first
clicks and outcomes, with concise literal labels. A generic Practice action must
truthfully launch an existing authored sequence with understandable scope; it must
not imply a broad personalized curriculum or silently replace learner choice.

No-history first visit must work. No Continue/Resume promise while unfinished work
is ephemeral. Keep optional record/remembering, About/credit and settings discoverable
but secondary. Do not move essential learner controls into reviewer-only settings or
label all gear capabilities as developer-only. Distinguish public settings from
inspection controls without changing their policy. Do not make history opt-in a
prerequisite for the primary action.

Map every current practice goal and supported fragment to its place in the proposal.
Preserve registry/capability-driven availability and transparent grouping. Keep
unimplemented goals absent, not disabled teaser buttons. Show how two hypothetical
future task families would fit without adding first-screen buttons; label them as
examples only, never current capabilities.

Provide first visit, choose/browse/back, session start/return, optional record open,
keyboard/linear participation and narrow/Chromebook/enlarged-text arrangements.
Propose first-Tab and return-focus contracts explicitly rather than hiding old
controls to preserve obsolete assertions. Reflow should include the known title
overflow and an honest account of how the proposed layout could address it in a
future source slice. No claim of rendered/AT validation from sketches.

List exact later source owners and affected registry/entry/route tests. A source
packet must use real mounted browse controls in witnesses rather than force-click
hidden historical buttons or bypass accessibility. Preserve goal semantics and
episode identities; any deliberate first-screen contract change needs owner adoption.
