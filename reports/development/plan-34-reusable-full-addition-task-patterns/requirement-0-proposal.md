## Proposed authored model and validation

Use exactly two immutable pattern identities, separate from problem IDs:

* `full-addition.construct-equivalent@1`
* `full-addition.inspect-keep-repair@1`

Use one new definition identity/revision for the compact task family, proposed as `phase-3-reusable-full-addition@1`, with `includeReflection: false`, the existing addition selector/grammar identity, and explicit pattern-aware schedule semantics. Add a new practice set revision (proposed `unlike-addition-vetted-set@5`) that retains all 11 current numeric item identities and their order, while updating the task association on the three named existing items to the new compact definition and pattern identities. This keeps the bank at 11, does not create additional numerical records or learner repeats, and leaves all old definition and replay identities reconstructable for their historical envelopes. The three mappings are fixed before construction: first item to construct; second and third to inspect/keep/repair. Each association pins item ID, fixture ID and authoring revision, definition ID/revision, pattern ID/revision, target `12`, and Plan 34 task-data revision. Other eight associations continue using their current definitions and authored behavior. Do not expose pattern choices as entry-page controls.

Store inspect stimuli in a dedicated versioned Plan 34 authored-task record collection, not in mathematical problem records and not as expected-answer tables. Each record holds the exact problem identity, target, pattern ID/revision, and one candidate form per active renaming side. For the initial three associations, candidate pairs can use the addendum's distinct profiles: on `1/2 + 1/3`, false left `5/12` and valid right `4/12`; on `1/3 + 1/4`, valid left `4/12` and false right `7/12`. For construct evidence, a compatible authored inspect record/profile is also needed for `2/3 + 1/4` (both candidates valid, `8/12` and `3/12`). No candidate answers are authored. A pure admission/materialization validator uses exact fraction equality and exact `convertToDenominator` semantics to check candidate truth, target compatibility, bounds, complete required-side coverage, operation/definition compatibility, supported rendering path, and nonzero renaming count. It must reject unknown pattern identities, missing/extra sides, malformed/out-of-range candidates, target mismatch, unsupported item/definition revision, or content whose sides need no conversion. Do not fall back to a default pattern or derive learner assignments from response/view/support.

For each six-pair compatibility test (3 problems × 2 patterns), execute the same shared admission/schedule/interaction functions with a fixed supplied pattern record; no per-problem branches. The pattern determines the response responsibility at transform entries and authored stimulus lookup, while item classification supplies the required side set and exact math supplies equivalence and operation truth. Thus a fourth compatible target-12 record needs a compact association and, for inspect, one complete candidate pair validated by the same generic rules; it does not need a new app/render/episode branch or an answer table.

## Schedule, established state, and intent contract

Add a narrowly named optional pattern context to construction for the new registered definition only. Legacy `computeBeatSchedule(instance, legacyDefinition)` stays byte-for-byte behaviorally equivalent. For the new versioned definition, validate the full item-plus-pattern association and candidate record before deriving and freezing exactly `encounter → transform entries for each problem-required renaming side in left/right order → operate → resolve`. The authored target is fixed to 12 and displayed as context (“Use twelfths”); it is not an intent. `encounter` remains an explicit learner acknowledgment. Reject zero-renaming content and unknown/incompatible pattern inputs before state creation.

New state must pin association/pattern/revision, target, candidate-data identity/revision when inspect applies, and immutable schedule. On encounter, establish the authored validated target/common unit as instructional state without a learner denominator-choice response. For construct, each transform asks only for the numerator and withholds the expected target form and corrected operand value until accepted. For inspect, each transform exposes only that side's authored candidate, with no correctness cue; the learner can `keep` or select `change top` and enter a numerator. Exact validation determines whether the candidate is valid and whether the submitted action was keep, valid unchanged change, false keep, valid repair, or invalid repair. A valid change to the same numerator is accepted as unchanged/valid and retains the submitted action. False keep and invalid repair recover at the same schedule entry. Only accepted forms feed operation. The operation accepts one complete numeric result; resolve is finish/continue navigation using the accepted exact value, with no second operation or reflection intent. Pattern, assignments, and schedule never change after help, error, retry, or view switch.

The projected form provenance must distinguish learner-constructed, authored-then-confirmed, learner-repaired, and item-provided forms. Retain the original inspect candidate, submitted action, exact classification, recovery, help history, and accepted form. Omitted notice/decide/reflect produce no learner evidence. The app should say no-help means unassisted-in-app only; it does not establish independence or mastery.

## Set lifecycle, support, access, prompt and help behavior

Version the existing set to revision 5 with the same 11 identities and order, changing only the three named items' versioned task association to the compact definition/pattern mapping. This keeps one learner goal, current numeric bank, current stable first item and the existing Next positions/exhaustion boundary. The per-problem task identity changes through its explicit definition/pattern association, not by minting a second numeric item. Retry keeps the item/pattern pair but clears all responses/help/recovery; Next is only available after resolution and selects the next fixed association; after the final existing item, current refusal/exhaustion behavior returns to choices; re-entry starts the old stable first item. Preserve selected view, support, and reviewer condition settings; no condition-specific extra question is added. Applicable transform conditions remain registered and selected; use existing declared-equivalence machinery when same output is justified because this definition has no reflection/condition-specific task. Do not silently rewrite selections or label omitted work as completed.

Both views show the same supplied source forms and target. Construct prompt: “Write the equivalent numerator for [source] in twelfths.” Use the existing fraction typography and a neutral target fraction template whose blank means unknown. Inspect prompt: “Is this form still the same amount? Keep it, or change the top number.” Candidate is initially unmarked. Controls are explicit `Keep this form` and `Change top number`, followed by a numeric top input and `Check` for repair. Keep immediately submits one action; valid repair requires choice plus submit. Explain local recovery: false keep asks learner to compare the parts and try again at the same form; invalid repair retains their draft and offers another try. Never show expected forms, validity text, answer summaries, or operation result before acceptance.

Help remains a learner-requested, task-local toggle at each transform. Construct help can adapt Plan 25's current multiplier support: show source-to-target factor equation; a submitted help multiplier remains separate support history and must not fill/accept the learner numerator. Inspect help may explain the invariant/method (“The top and bottom must scale by the same factor. Decide whether the displayed candidate keeps the same amount.”) but must not identify candidate validity, tell the learner keep/change, expose the corrected numerator, or accept an answer. Preserve a partially typed repair numerator when help opens/closes, and keep help visible in history after closing. In both views keep the current action/help controls adjacent to the active task and return focus according to established app behavior. Applicability is item/pattern-derived: no transformation support on omitted notice/decide/reflection; do not offer help that cannot be used. Plan 25's current help protocol currently recognizes only denominator choice/conversion and its multiplier input, so inspect help will require a narrowly scoped help kind/intent and both render paths, or a shared already-existing help form if investigation discovers one during approved implementation. Do not route it through generic escalation.
