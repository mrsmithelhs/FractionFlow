## Normalized contract and identity

Propose one IndexedDB database, one object store and a single validated root value. Schema/observation/projection revision `1` explicitly versions interpretation; exact keys, types, enums, lengths and total serialized size are checked on every read and write. Unknown or corrupt root: no rendering of stored text, no overwriting it automatically, and an unavailable/clear path. Unknown entry revisions or identities are excluded from descriptions, never reinterpreted. Reject unexpected keys and free-form data. No generic migration or silent assisted-to-unassisted upgrade. A reviewed future compatibility mapping is required for any different revision.

Each entry contains only: opaque random episode token (deduplication), monotonic sequence (stored order), registered item ID, exact set ID/revision, authoring revision, definition ID/revision, underlying comparison revision, recipe ID/revision, task data ID/revision, cue ID, fixed condition ID/revision, exact support-profile identifier/revision, first outcome (`accepted` or `retry`), final outcome (`accepted` or `unresolved`), and the two bounded assistance snapshots (the acceptance snapshot is null while unresolved). The known responsibility `compare-symbolic-fraction-magnitudes` and cue/support semantics are fixed by an explicit versioned admission registry, not inferred from ID alone. Registry revision 1 admits only the inspected live definition `phase-4-symbolic-fraction-comparison` revision 2, underlying revision 1, the vetted set and authored task/recipe data revision 1, the twelve registered items and their actual cue IDs; include current static condition and the exact high/medium support configurations under a dedicated support/cue contract revision. Any future change in cues, support, identity or meaning requires a bumped admission contract and explicit compatibility review. Store no source fraction values, relation, answer, construction numbers, event logs, session index, name, timestamps or learner identity. IDs and revisions distinguish task meaning; cue/support and assistance qualify interpretation; outcomes describe the event; sequence and token provide ordering/deduplication.

A versioned mapping recognizes reversed pairs 02/08, 03/04, 05/06 and 11/12 as the same pair for repetition labels. Other entries are not asserted independent. Individual entries only; no aggregated breadth, score, elapsed-time or ability claim. Retain newest 30 eligible records by sequence, evict oldest in the same transaction. This is a provisional storage/privacy cap, not a pedagogical threshold. No visit grouping is needed for individual ordered records.

## Lifetime and transaction proposal

Use IndexedDB readwrite transactions on the single root key for **every** enable, append/update, stop and clear. The root holds schema, enabled boolean, unpredictable generation token, next sequence and at most 30 validated entries. IndexedDB serializes overlapping readwrite transactions on the same object store; test actual browser behavior, abort/error and transaction completion rather than treating request success as a committed save. The adapter checks current enabled state and generation **inside the same transaction** before every write. A newly installed eligible episode gets a fresh random token and snapshots the current enabled generation; if not enabled/ready at installation it is ineligible for its entire lifetime. Thus enabling partway through cannot misstate earlier assistance; a fresh episode is needed. Per-episode async writes are ordered, and an update may upsert the same token only within its original generation. App generation and shell lifetime guard callbacks; replacement/restart creates a fresh token and invalidates old callback work. A committed retry already stands without a teardown write. Once stop/clear commits, pending writes with an old generation cannot write; work committed earlier is handled by the stop/clear transaction. Handle transaction aborts and late completions without announcing success or reintroducing state.

Clear atomically replaces the root with **empty entries, a fresh generation and sequence reset**, retaining the current enabled preference. It removes all learner observations and their tokens; the minimal fresh generation/preference root remains solely to invalidate stale writers and honor the explicit choice. Stopping atomically sets enabled false and rotates generation, retaining prior entries for inspection until clear; starting again rotates generation and keeps entries. Both stop and clear invalidate in-flight/old episode snapshots across tabs. A tab must read the root in its transaction rather than trust a local cache; use `versionchange`/visibility refresh for UI, with transactional checks authoritative. If database open, transaction, randomness or validated state cannot be used, remembering is unavailable, no save is claimed, and practice continues. An unsuccessful clear is reported as unsuccessful, not represented as deletion. An inaccessible/corrupt database must offer a clearly labeled explicit reset/delete action whose success is only acknowledged after completion; blocked deletion must report failure. Avoid automatic destructive recovery. Browser storage eviction/private mode may remove the database. Test multi-tab clear/write, concurrent upserts, duplicate token, stop/start, stale callbacks, malformed roots and blocked/failing transactions in actual browsers; pure fakes do not establish browser guarantees.

## Proposed concise interface and copy

On the entry page, place a compact collapsed **Practice record** control below practice choices, never a dashboard or a prerequisite. In its panel:

- First visit, off: “Remember comparison activity on this browser? This browser may be shared. Records can be cleared or lost.” Buttons **Start remembering** and **Close**. Practice choices remain available without enabling.
- Returning, on: “Remembering comparison activity on this browser. Anyone using this browser may add to or see it.” Buttons **View record**, **Stop remembering**, **Clear record**; no repeated ownership question. Off with retained data: “Not remembering. Earlier activity remains on this browser.” Offer **Start remembering**, **View record**, **Clear record**.
- Inspect: “Comparison activity on this browser” and stored-order individual entries. Examples: “Comparison: tried again, then accepted. Model used before the first choice; help used before the accepted choice.” “Comparison: first choice needed another try; no accepted choice recorded.” For unknown timing: “Assistance before this choice is unknown.” For no captured assistance: “No in-app help, model, or construction recorded before this choice.” Include an accurate item label and repeated-pair indicator only via registry; no personal pronouns or personal recommendation, since shared ownership is unknowable. Offer **Practice comparison** as a voluntary ordinary route and **Close**.
- Stop confirmation text: “Stop remembering? Earlier activity stays until you clear it.” Buttons **Stop remembering**, **Cancel**. Clear confirmation: “Clear comparison activity on this browser? Remembering stays on/off.” Buttons **Clear record**, **Cancel**, reflecting actual current preference. Never claim success before commit.
- Storage failure: “Practice is available, but this browser could not save the record.” On failed clear: “The record could not be cleared. Please try again.” On incompatible/corrupt data: “This record cannot be read. You can clear it.” Clear/reset may itself fail and must say so. No underlying stored text is interpolated into DOM.

Valid retry then correction updates one entry; leaving after a valid retry leaves an unresolved entry. Existing session exit copy remains truthful because it speaks about the place, not task activity. ## Binding orchestration refinements received 2026-11-04

An observation admitted while its episode is live is copied immediately into an immutable normalized snapshot. Retiring the episode through Next, exit or restart must not discard that already-admitted queued write; no reference to old episode state is retained. A stale callback cannot admit a new observation or mutate current UI. Clear/stop generation checks in the transaction remain authoritative even for already-admitted snapshots. Per-episode queue ordering must preserve delayed retry followed by acceptance and then Next. An update to an entry already evicted by the 30-entry cap must not reinsert it or evict a newer entry; exercise eviction/update ordering and clear/stop races at the checkpoint.

Derive identity admission from authoritative registered definitions and validated contexts where possible, with an explicit versioned compatibility contract for semantics; do not maintain an unnecessary parallel content catalog. Default learner-facing entries use brief language such as “Compared correctly” or “Tried again, then compared correctly”; detailed assistance is optional detail, and internal “accepted” and revision identifiers are not default UI. For enable or clear during an installed episode, say “A new problem is needed before activity can be remembered.” Continue the current problem without blocking practice. These refinements supplement the proposal above and supersede conflicting examples or generation wording.
