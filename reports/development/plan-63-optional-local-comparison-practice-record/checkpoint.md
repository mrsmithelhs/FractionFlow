## What exists and evidence

`src/app/comparison-record.js` validates exact allowlisted normalized root/entry/identity shapes, known revision, registered Plan49 contexts, outcome/assistance combinations, order and 30-entry cap; it projects individual entries and reversed-pair repetition without a breadth claim. `createRecordAdmission` captures immutable normalized work once per live episode; retirement refuses new work but does not invalidate previously returned snapshots. `comparison-record-storage.js` serializes the root operations in IndexedDB readwrite transactions, checks enabled/generation inside each, and acknowledges transaction completion. Stop retains entries and rotates generation; ordinary Clear retains enabled preference, empties entries and rotates generation. Explicit recovery replaces an unreadable root atomically with an empty **disabled** fresh generation; reset requires an explicit UI action and must disclose that it stops remembering. If opening or replacement fails, it reports failure rather than deleting the database later. No payload text is rendered.

## Boundaries and integration obligations

Deduplication is within retained records. An acceptance for an evicted token returns `missing`; it cannot reinsert an old record. No unbounded tombstones are kept: an arbitrary replay of a first-observation token after eviction is not a supported adapter operation and could insert it again. Integration must use one admission object per installed live episode, prohibit retired callbacks from new admission, preserve ordered already-admitted retry then acceptance snapshots across Next/exit/restart, and never automatically replay an old first payload after uncertain completion. An uncertain/failed save must be reported honestly while practice remains usable. Current pure tests demonstrate the admission primitive, not actual app lifecycle wiring; the later integration gate must prove both launch paths, rapid navigation, teardown/remount and UI behavior. Clear/stop must invalidate pending observations transactionally, not merely through UI state.

The adapter rejects the entire unreadable/incompatible root from projection rather than exposing or upgrading unknown data. An explicitly requested reset is destructive and turns remembering off; unavailable/open-blocked storage must remain a reported failure. Reset is distinct from ordinary clear. Compatibility depends on the explicit contract revision being bumped when task, condition, cue or support semantics change. Exact support and condition verification against installed state and safe assistance extraction remain integration responsibilities; the pure module accepts only normalized support categories and snapshots and does not assert their provenance. No raw answers or session state are stored by these modules.

Tests have not induced a real browser quota exhaustion, browser process crash, unsupported browser, blocked upgrade, or hardware loss. They do not establish durability.
