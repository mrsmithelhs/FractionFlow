# Plan 65 — Entry organization design

Status: investigator recommendation for orchestrator review and owner adoption, not an implemented or accepted interface. Source inspection pinned to `366b531eb3308448f2c5ab3de8791fa9398dc950`; the subsequent `f780e46` records scope approval, not a source change. See `scope-approval.md` and `reachability-map.md`. This is a static, unrendered design; no learner, rendered-browser or assistive-technology validation was performed.

## Recommendation and owner choice

Recommend **an expandable browse section on the start page**, initially closed. It avoids an extra page transition while keeping the list out of the first screen. Preserve the current arithmetic-first emphasis for the first slice: the first action remains **“Add fractions with different denominators”**, launching its existing authored set from the beginning. Follow it with **“Choose what to practice”**. This is a specific practice choice, not a general or personalized Practice promise. Offer the existing four-episode session inside browse under Compare and distance, labelled **“Compare fractions, then find a distance”**, with the existing concise cue **“Your place in this practice is not saved.”**

This keeps the existing first-Tab goal and the product's addition/subtraction emphasis while making other goals one disclosure away. The tradeoff is that a learner seeking subtraction, comparison or number lines takes another action, and the expanded page can be long. Group headings and an ordinary vertical list preserve scanning without adding explanations to every choice. The owner may instead choose the four-episode session as the first action: use the literal label above, add **“4 problems: compare fractions and find a distance.”**, and move the arithmetic action into browse. That gives a finite cross-type experience but makes comparison/distance the first emphasis and changes first Tab; it must not be presented as a complete curriculum or tailored selection. Both alternatives work without a record. No third layout or scheduler is implied.

### Two layouts considered

| | Expandable section (recommended) | Dedicated browse view |
| --- | --- | --- |
| Start | Primary action, then “Choose what to practice”; record, settings and About remain reachable. | Same start. |
| Choose | Activating the disclosure reveals grouped real buttons below it; `aria-expanded` reflects state. Focus remains on its control; next Tab enters the first available goal. | Opens a separate browse region; focus moves to its heading. Back returns to the start and focuses “Choose what to practice”. |
| Tradeoff | Familiar disclosure and no extra page; longer page when open needs reflow and scroll checks. | Shorter distinct screens; extra navigation and state/focus complexity. |
| Episode return | Both deliberately return to the actual start, with browse closed and focus on the start heading, preserving Plan 64. | Same; no implicit return to browse. |

A native disclosure or equivalently accessible button/region is acceptable only if its keyboard, expanded state and focus behavior meet the contract. Do not require all groups to be expanded on first visit; this design proposes one disclosure, not nested controls. Repeating the default goal in browse is intentional so the goal inventory is complete; both controls call the same registered type.

## Interaction contracts for a future slice

- **First visit and first Tab:** No saved history required; first Tab lands on the literal arithmetic launch. Tab then reaches Choose, Settings, Practice record and About in the shown order (with any controls in an opened disclosure participating in normal DOM order). The heading is programmatically focusable for return, not a first-Tab stop. The existing gear's historical second-Tab assertion is intentionally revised only after adoption; do not conceal reachable controls to satisfy it.
- **Browse/back:** Activate Choose to expand; focus stays on Choose, then Tab enters available goals in group order. Activate again to collapse; focus stays on Choose. If a future UI allows closing while focus is inside, restore it to Choose before hiding the focused control. No separate Back button is needed in this option. Buttons reflect admitted registry capabilities; skip an empty group and avoid disabled previews. Group metadata must not become a second registry of which practices exist; fail visibly in development if an admitted goal lacks a group rather than silently dropping it.
- **Launch and return:** A goal button starts its exact registered type and item identity as today, updates its existing fragment, and focuses the episode landmark on success. The session starts its fixed manifest, clears the fragment, focuses the episode, and is ephemeral. Back to start, including after a browse launch, returns to the actual start with the disclosure closed and focus on the entry heading. Standalone return is immediate; session exit keeps the Plan 64 unfinished-session confirmation, Stay/Escape focus restoration, accepted-episode exceptions and loss wording. No retained browse destination is proposed. Fragment launch bypasses browse but uses the same actual episode and returns to the same start. Unknown/malformed fragments retain existing fallback behavior.
- **Failure:** A session preparation failure keeps start available and focuses its existing neutral notice; committed display failure exits safely with its existing notice, not a rollback promise. Preserve standalone preparation/refusal behavior and make any newly introduced browse mapping failure observable; never navigate to a hidden or nonexistent control. Test stale callbacks and focus after each failure. No new loss policy is proposed.
- **Record:** The `Practice record` disclosure remains secondary and discoverable from start. Its existing opt-in, view, stop, clear and reset flows and shared/lost browser language remain intact. Its “Practice comparison” action directly launches the existing comparison type and fragment, with episode focus and ordinary Back to start behavior. An unavailable record never blocks practice. Record only eligible comparison observations under Plan 63, including the existing session coverage; it is not saved position or a selector.
- **Settings and accessibility:** Keep the gear reachable from start with a meaningful accessible name. Separate the public **Support level** choices (More support / Less support) from the Phase 2 display-condition inspection choices in presentation and labels without changing their effect, eligibility or policy. Do not call support developer-only. Preserve keyboard-operable controls, visible focus, visual/linear view switch and equivalent participation in episodes, touch targets, reduced-motion behavior and all task-owned Help. Inspect the exact current applicability/disabled states before designing the source change; do not promise that every condition applies everywhere.

## Reflow and validation plan

Use a single flexible column with wrapping labels, no fixed-height rows, logical DOM order and scroll access to every control. At narrow phone width, Chromebook-sized viewport and enlarged text, check the closed start and expanded groups, settings/record disclosures, focus visibility, clipping and horizontal scrolling. The known enlarged-text **FractionFlow title overflow** is a distinct existing issue: a future slice should inspect the title's font sizing, width, wrapping/overflow behavior and long unbroken word, then choose and test a restrained fitting strategy without truncating its accessible name. This sketch does not prove a CSS fix or actual device, zoom, screen-reader or learner usability. Include 200% text/zoom and constrained-width browser checks, keyboard and linear journeys, and human accessibility review appropriate to the project's participation floor; report exact conditions and limitations.

## Proposed first implementation packet, after adoption

A single scoped entry-shell change may implement the chosen primary, accessible browse disclosure, registry-driven group projection, current labels, secondary controls and title reflow. No new mathematical content, episode identities, scheduler, adaptation, history extension or exit-policy change. Source ownership candidates: `src/app/app.js` for shell, route and focus integration; `src/app/practice-types.js` for transparent grouping metadata only if necessary; `src/app/styles.css` for responsive entry; `src/render/strings.js` if shared copy is moved there. Preserve `src/app/magnitude-session.js`, `src/app/comparison-record-panel.js` and controller semantics unless a narrowly justified integration seam is approved. Actual file scope and serialization need a separate packet mechanism gate.

Target `tests/entry-page.test.js`, `tests/app-shell.test.js`, `tests/app-plan60-mounted.test.js`, `tests/app-plan63-repair01.test.js`, registry/set tests, and route witnesses in `tests/routes/route-matrix.json`, `tests/route-contract.test.js`, `scripts/dev/run-route-matrix.js` and applicable `scripts/dev/plan*-route*.mjs`. Audit their actual use before editing: some depend on legacy fixtures or immutable route hashes, so preserve historical witnesses and add or migrate current ones deliberately. In every current-entry witness, open the real mounted disclosure and activate a visible goal; no force-clicking a hidden historical button, synthetic direct handler invocation, or accessibility bypass. Cover each current registry ID and fragment, primary/session/record launch, first Tab, collapse/focus, return, unknown hash, errors and settings. Verify availability changes with a representative injected registry including an empty group and missing mapping. Route checks should observe the expected actual episode identity, not just URL changes.

Risks: first-screen emphasis and first-Tab change if owner chooses the session; duplicate default control; historical selectors and pinned witness hashes; registry additions without group metadata; data loss wording and focus regressions; title fit at large text. Preserve actual authored meanings and existing storage policy. Scope approval is not owner adoption, source authorization, accessibility certification or deployment.

**Owner-review tradeoffs and configuration:** The repeated primary goal in browse is intentional so the complete inventory remains visible there. Closing browse on Back to start means a learner choosing a different goal must reopen it; this is a design tradeoff, not demonstrated usability. The future primary-launch choice and group assignments should be explicit configuration derived from admitted registry/session capabilities, validated against those owners and their availability. Do not create a second hand-maintained practice catalog or permanently hardcode an arithmetic-versus-session branch; this is not an adaptive selection policy. An unavailable configured primary must fail safely and visibly during development rather than silently inventing a replacement.
