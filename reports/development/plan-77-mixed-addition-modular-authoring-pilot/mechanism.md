## Present path and constraints

`src/content/plan74-mixed-addition-task.js` contains tuple operands expanded to records, `PLAN74_IDENTITY`, exact operand validation and result derivation, exact live-record admission, and context resolution/validation. The records are `plan74-add-01` revision 1 (1 3/8 + 2 5/8) and `plan74-add-02` revision 1 (1 5/8 + 2 6/8), in that order. The set is `mixed-number-addition-with-regrouping` revision 1 and definition `phase-5-mixed-number-addition-with-regrouping` revision 1. The current validator requires positive decimal strings, proper fractions, eighths, and a pooled numerator from 8 through 15; it derives and cross-checks exact results in the math core. Admission additionally requires exact equality with a live record, and context validation requires equality with the resolved live context.

`src/app/practice-types.js` maps `PLAN74_RECORDS` in order to the live chooser; `src/app/app.js` resolves each selected item ID. Episode and scene validate context; the episode uses `admitPlan74Record` for the answer. `src/interaction/replay.js` v17 checks the entire context, set/item reconstruction identity, definition, and intents before resolving the live item again. Thus widening admission or adding trial records to `PLAN74_RECORDS` would affect launch and replay, not merely authoring. The episode's whole response field is bounded at 4 and pieces at 16: arithmetic eligibility alone does not establish that every possible positive-whole candidate can be completed in the mounted task.

- Add Plan 74-specific data module(s) under `src/content/data/`: compact records with item ID, item revision and the two authored whole/numerator/denominator strings, plus an explicit ordered membership list keyed by set ID and revision. Keep both existing records and membership exactly as above; no derived answer in data. Separate data and membership exports may live in one small file if that is sufficient; no generic registry.
- Keep `plan74-mixed-addition-task.js` the owner of task-specific validation, exact result derivation, membership checking and context materialization. Construct the existing frozen `PLAN74_RECORDS` export from the ordered live membership, retaining its current record shape and all existing exports, errors, acceptance behavior and context shape. Fail closed on missing, duplicate or ambiguous record IDs, duplicate membership, unknown references and invalid records. New diagnostic authoring validation should identify item and reason without replacing or weakening the existing consumer-facing checks. Treat item revisions and set revisions as explicit identity, not inferred from order.
- A separate repeatable authoring validator can accept an explicitly supplied candidate record collection and trial membership without registering either with the app. Check schema, duplicate IDs, membership references/duplicates, current arithmetic eligibility and task reachability (including the episode's whole-field bound). Keep any stricter pilot reachability check separate from the existing `validatePlan74Operands` contract. Report each failure with item or membership reference and reason. Never make arbitrary eligible candidates pass `admitPlan74Record` or `validatePlan74Context` in the live build.
- Historical set revision 1, record contents/order and exported contexts stay immutable. Verify against pre-change captured v17 envelopes for both live items, plus current replay and tamper tests; do not regenerate historical fixtures after the change and call that compatibility. ## Baseline edit exercise and matching trial protocol

This is a source-inspection walkthrough, not a timed authoring run: to add an eligible record to the present live path, an author edits the tuple list in `plan74-mixed-addition-task.js`, assigning ID/revision and operands; the same list implicitly supplies membership and order, and app registration consumes every entry. No separate validator gives item-specific reasons; `validatePlan74Operands` throws the generic `invalid mixed-number addition content`. A candidate can be checked directly with that function, but actual episode admission requires changing the live list. This establishes observed edit sites and diagnostic limitation, not measured ease, elapsed effort, or a completed baseline trial.

Before either comparable exercise, orchestration should approve the following shared brief and case coverage: add three fresh, unique, valid eighths records, including one zero remainder and two different nonzero remainders, with organized whole result at most 4; diagnose and correct one deliberately below-one item. Use distinct IDs; no supplied operand examples. Freeze the precise held-out operands and invalid stimulus with orchestration, unseen by the seam writer and independent pilot author until assigned. The baseline arm uses an isolated checkout pinned to the baseline and a short factual baseline task brief with the same input and expected outcomes; the pilot arm uses a separate checkout pinned to the approved seam and only its authoring guide, same brief and case coverage. Neither checkout's trial changes enter the live bank. Record the precise pin, author/model and context, start/end evidence, opened and edited paths, source vs data edits, commands, diagnostic text, wrong guesses, correction passes and dependencies. Run the same arithmetic, uniqueness, membership, result-bound and case-coverage checks against all three final records. Preserve raw observations and distinguish setup/validation cost from edits; report missing time/token information as unavailable.

For a discriminating mounted-task witness, an isolated test checkout may temporarily substitute the trial set's membership and records into the existing live export, then run the unchanged mounted task on one nonzero case and demonstrate an accepted answer; label the substitution and evidence experimental, never merge it, and verify the real checkout still exports only the original two. The normal live admission intentionally excludes trial items, so a generic-validator pass alone is not a mounted-task witness. If this substitution cannot be performed without changing protected shared app, renderer, or replay dispatch, record the limitation and stop for orchestration rather than widening scope.

Predeclared success requires: both original records, order, exports, context and v17 replay unchanged; malformed/duplicate/ineligible records and invalid membership rejected with actionable diagnostics; all held-out trial records pass generic checks; the invalid item is diagnosed and corrected; trial records remain outside the real live bank; and a discriminating mounted witness succeeds where the isolated setup supports it. Compare source and data edits per record independently from observed comprehension/corrections. A failure, unavailable isolated author, or ambiguous observation is an adjustment/defer result, not proof of improvement. One pair of exercises cannot establish general author productivity or learner outcomes.
