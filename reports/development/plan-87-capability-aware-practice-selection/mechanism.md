## Proposed draw and rollout

For a fresh standalone launch, take at most **four** distinct items from that button's own admitted, versioned bank. Use all eligible items if there are one to three; one is a valid finite draw, not an excuse to repeat. If none can be verified usable, keep the entry page usable, do not launch, and show a focused, concise unavailable notice. A fresh launch gets a fresh in-memory 32-bit seed; the same result can occur twice. A specified seed, algorithm version and identical canonical eligible identity list produce the same draw. Sort full `(set ID, revision, item ID)` identities canonically, use a specified versioned 32-bit PRNG and Fisher–Yates shuffle with unbiased bounded draws, then take the first four. The implementation must define its exact PRNG and bounded-integer algorithm in tests, including known-answer vectors; never depend on platform sort or random behavior. No difficulty ranking or learner data enters selection.

Initially keep the four Plan 89 expanded sets behind a report-local review harness, injecting the actual registered sets through `createFractionFlowApp` as Plan 89 did, with no public route or normal chooser change. Keep current production bank memberships and explicit fixed routes intact. Following mechanism approval, prove selection against real registered records and fit evidence; owner rendered review and a **separate** owner decision are required before expanded sets become ordinary chooser candidates. This proposal does not authorize new numerical bounds, materializers or representations.

## Fit evidence and launch

Eligibility is the intersection of admitted membership, a task/representation-specific verified fit class, and the current measured working area. Before selection, measure the actual available content/representation box in CSS pixels and relevant computed text sizing; also check the real controls, labels and participating visual and linear paths. Use item-specific features that govern the actual task, including partition density, labels, response controls and help/alternate views, not device names, physical density or support level as a proxy. Geometry, text wrapping, touch targets, keyboard/focus, overflow and usable equivalent participation must be checked across the full episode, including resize and zoom. The fit registry must be conservative and trace each class and threshold to production-faithful observations. A layout threshold is an implementation proposal only after those measurements; do not infer one from Plan 85's disposable bridge mock or Plan 89's two mounted layouts.

Define a **conservative class** only for records and conditions actually verified at narrow/enlarged layouts and with a usable continuation if the layout later shrinks. Unknown, zero, stale, non-finite or unavailable measurements, and enlarged text for which a wider class has not been verified, select only that class. A class is not safe at arbitrary size: if the current working area is below the verified minimum, or a safe measurement cannot establish the minimum, do not launch until a verified equivalent participation path is available; otherwise show the unavailable notice. Do not silently use an unverified legacy item as a fallback. The conservative class may be empty pending evidence. Measurement failures must never expand eligibility. No viewport profile or preference is persisted.

**Same-bank example, deliberately illustrative, not a claim about specific records:** within Plan 40 v3, suppose evidence classifies registered IDs A and B as conservative and ID C as requiring a verified wider bar/control layout. At a measured narrow working area, eligible IDs are A and B; at a verified wide area they are A, B and C. Each uses the same v3 identity and unchanged math. Enlarged text or unknown measurement removes C unless its own combination is verified; if the safe minimum cannot be established, the no-launch notice applies. The actual IDs, thresholds and measurements must be reported before this example becomes an enabled policy. Plan 89's 360×740 visual and 1093×740 linear/200% CSS-root journeys are useful evidence, not item-level breakpoints or proof of actual browser zoom, devices, assistive speech or learning.

## Lifecycle and resizing

A launch installs the selected first identity and normal exact episode state. Retry restarts that same item under the existing retry contract; an incorrect response remains the episode's ordinary recovery, not a new draw. Next after completion advances to the next eligible unstarted identity; after the last, use the existing natural completion and return to start. Exit/refusal, focus, error recovery and record semantics retain existing shell contracts.

Resize, zoom or visual/linear view changes never replace, restart or recompute the active problem, exact answer, instructional state, draft, help or focus. Every newly eligible item must first demonstrate an in-episode responsive reflow or equivalent usable participation path down to the verified minimum; otherwise it is not eligible. Do not silently switch the learner's chosen view. At a shrink, remeasure before Next and recheck only unstarted identities. Keep surviving planned identities in order; deterministically fill vacated positions from the original seeded full-bank permutation, in order, subject to current eligibility and excluding every previously started or still-planned identity. If insufficient, shorten the remainder and finish naturally. Recheck again before each launch to handle intervening changes; growth does not lengthen or reorder the current draw. If even the active item's verified continuation cannot be provided, retain its state and present an accessible recovery/space-needed path rather than replacing or discarding it. The exact presentation of that recovery requires verification before inclusion.

Example: draw A, C, B, D at wide size. While C is active with a draft, the area shrinks: C and its draft stay; if D no longer fits, retain B and replace D with the first eligible unused identity in the original permutation, or finish after B if none remains. Retrying C cannot consume another identity. Replacement must preserve the original cap and never repeat a started identity.

## Managed practice and protected behavior

`src/app/magnitude-session.js` currently defines the scheduled three-slot mix: comparison (02 or 09), comparison (10), then distance (01 or 04), with exact admission and duplicate-pair checks. `src/app/app.js` routes **Start a practice session** to that scheduler; the separate **Compare fractions, then find a distance** entry uses its fixed magnitude manifest. Filter choices within each scheduled slot, preserve slot order, two comparison plus one distance and its pair/identity constraints, and preflight the entire resulting manifest. A seed selects deterministically among valid combinations; no valid combination means try the existing fixed comparison fallback only if every member is verified fit, otherwise keep entry usable and show the notice. Never substitute a different type to fill a slot or silently shorten the type mix. On shrink retain the active episode; reselect only unstarted slot choices using the same deterministic order and constraints, or finish early if no valid remainder. Admission must validate the resulting constrained manifest, not accept arbitrary manifests. Preserve both literal manifests and the explicitly authored Plan 69 comparison route under their own existing rules; do not silently filter or rewrite fixed review sequences or legacy direct routes. If their own verified participation path is unavailable, fail safely rather than changing their identities.

## Replay and diagnostics

Keep historical envelope schemas, set memberships, legacy fixture identities and exact reconstruction unchanged, including Plan 40 v1/v2/v3 and mixed-family v1/v2. No profile is recorded. It is not an episode replay format, analytics, or a new persistence commitment. A seed alone is insufficient when eligibility changes. Verify Plan 63 coverage explicitly for actual selected contexts; do not infer that new session membership automatically enters history.
