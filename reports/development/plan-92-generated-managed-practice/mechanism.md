## Atomic Clear, old tabs and failure cases

Existing `fractionflow-comparison-record-v1` IndexedDB version 1 stores an exact-schema root in object store `record`; its clear replaces that root with a fresh generation in a readwrite transaction. Proposed migration upgrades **that same database** to version 2 and adds the expanded store; preserve the validated legacy root and enabled flag. Upgrade is exclusive: live compliant v1 connections receive versionchange and close, and an old app attempting `open(name, 1)` after upgrade must fail with VersionError. A blocked upgrade, old tab that does not close, storage failure, unavailable crypto or unverified browser behavior means no expanded consent/selection; keep no-history practice, explain the issue and do not claim a reset succeeded. Verify this with actual supported old-app code, not just a simulated flag. Existing legacy comparison remains independently available where safe; no separate epoch alone can fence old writers.

After successful upgrade use one readwrite transaction spanning legacy root and expanded store for Clear: rotate authoritative epoch/generations, replace legacy root with empty root preserving its enabled flag, delete expanded observations and derived evidence and establish fresh bounded coverage preserving expanded enabled flag. Every expanded write checks epoch and enabled state in the same transaction as its mutation; legacy writes use the rotated legacy generation. Event writes, Clear and history-aware selection validation serialize on the common store scope. For in-flight operations: write before Clear is erased by Clear; Clear before write causes stale-generation refusal. A cached snapshot and prepared Start/Next choice carry epoch and selection revision. Before installing any history-derived choice validate the authoritative epoch transactionally, and establish a commit protocol that serializes validation/install against Clear; merely checking then asynchronously mounting is insufficient. A cross-tab lock shared by Clear and choice installation (e.g. Web Locks where supported), with the epoch transaction inside the lock and no asynchronous gap between final validation and synchronous install, is proposed; fail closed to no-history/replan if the lock is unavailable, lost or transaction/installation fails. Define and test lock ordering, completion, rollback and crash release. Notifications are hints to retire caches, never the authority. An already installed episode and draft survive Clear, but its prior observation admission is retired; next Start reads fresh empty state and an unstarted stale choice is discarded and replanned. Both Clear-before-delayed-choice and choice-before-Clear, plus Next, writes, stop, reopen, corruption and notification loss require two real browser contexts/tabs and old-version fixtures. If these guarantees cannot be proven, stop for owner disposition on erasure and migration, not a weaker claim.
