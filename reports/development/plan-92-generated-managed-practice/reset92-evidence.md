# Plan 92 — isolated reset and consent preparation

This is a **test fixture and protocol investigation**, not production migration, expanded remembering, a consent control or a passed reset gate. `reset92-probe.mjs` runs two same-origin pages in one fresh Chrome browser context against uniquely named disposable IndexedDB databases. The actual existing version-1 comparison storage adapter is used in the old page; `reset92-fixture.js` implements a deliberately small synthetic version-2 store and lock protocol. No ordinary app or learner record is touched. Results and browser version are in `reset92-observations.json`.

The run established, in this fixture: a live v1 connection cooperatively closed for upgrade; its actual v1 adapter then received `VersionError` on reopening the v2 database; the enabled legacy root survived the upgrade. A v2 transaction preserved both synthetic enabled flags, erased prior test entries on Clear and changed the epoch; a delayed old-epoch write and choice were refused. A choice already installed remained represented after Clear. In another ordering a held choice acquired the common Web Lock and validated, Clear visibly queued, the choice installed and only then did Clear finish. A deliberately non-closing v1 connection caused the upgrade request to report blocked; after it closed, the retired request left the database at version 1. Stop invalidated a prior epoch, and an unavailable lock produced refusal. These are synthetic observations with explicit sequencing, not proof of the production scheduler, asynchronous app rendering, old UI messaging or every race.

Proposed production boundary remains the approved mechanism: upgrade the same database only within the separately consented path, preserve existing legacy root and flag, use an upgraded legacy adapter, and keep the expanded flag independently off until affirmative consent. In one transaction spanning both stores, Clear replaces the validated legacy root with an empty root preserving its flag, advances both generations, and clears expanded data while preserving its separate flag. Stop retains prior data but rotates the epoch and disables future observations. Writes atomically compare epoch and enabled status with mutation. Hold an origin-scoped Web Lock across authoritative epoch/consent revalidation and synchronous installation of history-derived Start/Next choices; Clear and Stop take that same lock, and no asynchronous gap may allow a stale installation after validation. If locking, validation, upgrade, crypto or transaction fails, do not claim success; use no-history practice. Broadcast notifications are hints only.

Still required: prove actual legacy root bytes and enabled/disabled states survive a migration, production blocked-request retirement and late unblocking, writes in both true concurrent transaction orderings, old app user-facing behavior and legacy controller integration, real mounted Start and Next with drafts, rollback and stale-choice refusal, Stop/enable/Clear controls, consent text and inspection, corruption/quota/transaction failures, notification loss, Web Lock crash release, and same-origin two-tab tests with the actual production adapter and scheduler. A new adapter must avoid opening version 1 after migration; old builds necessarily fail closed rather than continuing legacy recording. The owner must be told if real migration cannot preserve the agreed record or erasure semantics. No observation or scheduling use is enabled by this experiment.
