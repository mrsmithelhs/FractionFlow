# Plan 49 — pure checkpoint 1

Date: 2026-11-01. Disposition: submitted for orchestrator review; mounted integration and serializer changes remain gated.

## Deliverable and boundary

`src/interaction/plan49-comparison-construction.js` is an isolated revision-2 pure contract and safe projection. It is deliberately **not registered** with the existing general episode dispatcher, renderer, app or replay serializer; no new launch can reach it. It wraps a revision-1 comparison reducer internally to preserve the existing relation check, source-model lock and compare/resolve behavior, while exposing a revision-2 outer context and chronological intent/assistance records. On relation attempts the provenance record identifies revision 2 and contains the actual ordered assistance. This wrapper is a checkpoint mechanism, not a claim that general episode state, scene validation or replay already accepts revision 2. Integration will require an explicitly reviewed adapter/registration and preservation of the identity mapping below. In particular the existing serializer must not be used on this wrapper before the v10 implementation is approved and tested.

The validated revision-2 context is the exact Plan 45 authoritative context with `definitionRevision` changed to `"2"`; validation converts only that value to `"1"` for the existing strict authoritative check. Definition identity is `{id:"phase-4-symbolic-fraction-comparison",revision:"2"}`. Records and source order are unchanged. The 144 positive common-denominator limit is separate from exact validity and any bar limit. Validity is tested first. `144` is admitted when common; a common target above 144 is unavailable; a non-common value above 144 remains not common. No derived target or form is filled by the renderer.

## Literal contract

All objects below have exactly the listed keys; extra keys are refused. `phase` is an explicit origin token, checked against current phase; mounted callbacks must additionally be scoped to item, generation and render. Proposed values are canonical decimal strings `0` or a nonzero digit followed by up to 29 digits. Empty, signed, leading-zero, non-string or longer wires are refused atomically; the app is responsible for keeping malformed raw text and presenting local validation. Zero is a well-formed wrong response. This length bound avoids unbounded integer parsing; it is distinct from mathematical validity and the 144 workspace cap.

- Existing `request-comparison-model` (`side`), `request-comparison-help` (`helpKind`) and `submit-fraction-comparison` (`proposed`) keep revision-1 literal validation and meaning. Same model side is a no-op; other side is refused. Relation can be submitted during any construction phase; correct relation resolves immediately and further intents are refused.
- `{type:"open-comparison-construction"}` moves inactive to denominator and records participation; another open is a no-op. Visibility/withdrawal is app-local, so neither close nor reopen clears work.
- `{type:"request-comparison-construction-help",helpKind:"denominator"|"multiplier",phase}` accepts denominator help only at denominator and multiplier help only at an active side before factor acceptance. Repeated request for the same phase, target and revision epoch is a no-op. New target revision has a new epoch and may request help again.
- `{type:"submit-comparison-denominator",phase:"denominator",proposed}` records a typed attempt. Valid admitted target progresses in first/second order; unchanged sides are accepted automatically as originals. Incorrect/unavailable attempts stay on denominator and give generic typed recovery.
- `{type:"submit-comparison-multiplier",phase:"first"|"second",proposed}` requires a current requested multiplier helper and no previously accepted factor. It checks the exact scale, records attempts and reveals only the accepted learner-supplied factor; wrong recovery reveals no expected factor.
- `{type:"submit-comparison-numerator",phase:"first"|"second",proposed}` validates the proposed form against the original and target with exact amount-preservation. Wrong entry remains on the side; success retains the learner form and advances. The factor helper is optional.
- `{type:"revise-comparison-denominator"}` is accepted only after a target and resets target, forms, factor and local recovery; a new epoch and `dependent-work-cleared` notice make invalidation explicit. History, original forms, relation draft (app-owned) and selected source model survive.

State contains `definition`, validated `taskContext`, internal `base`, `construction` (`epoch`, `phase`, `target`, `acceptedForms`, `multiplier`, `recovery`), chronological `intentHistory` and `assistanceHistory`, and separate typed helper `attempts`. Final relation attempts remain the underlying reducer's separate retry/provenance history. Fresh `createPlan49Episode` has no workspace state; Next/restart/re-entry must instantiate a fresh episode during later integration. Raw drafts, disclosure, view and focus remain app-owned and outside this pure contract. No actual mounted close/reopen, focus or stale-control guarantee is claimed here.

`projectPlan49Construction` projects source forms, permitted accepted forms, selected model, phase, target, recovery, request flag and accepted multiplier, with accepted relation only when resolved. It never returns an unconstructed numerator or an expected multiplier. For close-pair reasoning it projects a nonnumeric cue. The projection is a candidate pure seam: mounted scene/contract validation, avoidance of hidden DOM leaks, last-request cue display and accessible copy remain integration work. It is not the existing general scene and does not itself render prompts.

## Replay policy to implement after approval

Existing revision-1 definition/context remains bound to exact v9, its three intents, numerical cue, and v9 authoritative reconstruction. Proposed v10 preserves the existing v9 envelope key set and content-identity structure, with `schemaVersion: "fractionflow.episode-replay/v10"`, definition id above/revision `"2"`, authoritative revision-2 context, and chronological outer intent history using the literals above. V10 must reject revision 1 or any other definition; v9 must reject revision 2 and new intents. Reconstruct from the registered item then apply intents in order; reject malformed keys, phase mismatch, noncanonical wires and mutated context rather than migrating them. Unsent drafts/view/focus are never serialized. The literal v10 string follows the existing v1–v9 naming pattern; it is proposed, not an implemented wire. No old fixtures are regenerated or relabelled.

Pre-change `capture-v9-oracles.mjs` captured `v9-prechange-oracles.json` before source work: item 01 and equality item 03, each with reasoning request, first model, and relation attempt. The tests replay the full captured states, recreate their envelopes, and compare the historical cue (including item 01's numerical 15). These two cases are targeted evidence, not exhaustive historical replay proof.

## Integration adapter map — proposed for approval

**One public state.** General `createEpisode` for the registered comparison definition `phase-4-symbolic-fraction-comparison@2` returns a frozen `fractionflow.episode-state/v1` record with exactly the current comparison fields: `schemaVersion`, `status`, `revision`, `episodeDefinition`, `taskContext`, `activeCondition`, `beatSchedule`, `schedulePosition`, `support`, `beat`, `expectedResponse`, `pendingResponse`, `established`, `completedBeats`, `intentHistory`, `helpHistory`, `replayHistory`, `supportHistory`, `assistanceHistory`, `retryHistory`, `responseProvenance`, `assistance`, and `lastRecovery`, plus `construction` and `constructionAttempts`. `episodeDefinition` and authoritative `taskContext` identify revision 2. `assistance.modelChoice` owns the one-model lock; `construction` has the checkpoint's phase, epoch, target, accepted forms, accepted multiplier and recovery; `constructionAttempts` owns helper attempts. This public record alone is authoritative; there is no public `base`, shadow revision-1 state, or second competing history. A small comparison-specific adapter or shared pure helper may use temporary private revision-1-shaped values internally, but none escapes in state, snapshots, provenance, scenes or replay. Public revision starts at zero and increases once for every recorded, successfully applied non-no-op intent, including a well-formed wrong helper or relation attempt; refused intents and idempotent no-ops leave the state and revision unchanged.

**Routing and projection.** Register revision 2 alongside, not in place of, revision 1; validate its exact context against the same authoritative item with revision 2. General `createEpisode` and `applyIntent` route by registered definition to the comparison adapter. General snapshot dispatches to a revision-2 snapshot containing the public task context, accepted comparison, model choice, construction, construction attempts, assistance history and relation retry history; it must not expose a private intermediate. The existing compare/resolve schedule is computed for both revisions, with current task and available relation response projected from the public schedule/status; local helper phase is projected separately and never becomes a permanent scheduled beat. Scene and progression consume the same public `status`, `beat`, `schedulePosition`, `established` and `expectedResponse` as other comparison episodes. A correct original relation sets resolved/resolve and uses the existing shared Next/final Back path even when help is unfinished. No app or renderer `.base` branches are introduced. The projection exposes only accepted forms, allowed single model and non-answer-bearing feedback. Callback and draft origin checks include item, generation, render scope **and construction epoch and phase**, so revise to the same phase invalidates older controls.

**History, provenance and replay.** Public `intentHistory` is the sole complete chronological sequence of recorded learner actions, including comparison and helper intents. Public `assistanceHistory` records actual requests and construction participation/attempts in occurrence order; `constructionAttempts` and relation `retryHistory` remain distinct. Each relation provenance entry is built from the revision-2 public state before that submission, using its true revision-2 context/definition, actual ordered assistance and accepted construction progress; it must not present a revision-1 intermediate as evidence or invent independent work. V10 serializes only the public `intentHistory` as `learnerIntents` with the exact envelope keys `schemaVersion`, `contentIdentity`, `episodeDefinition`, `support`, `activeCondition`, `learnerIntents`, `taskContext`; it does not serialize private intermediates, drafts, disclosure, focus or view. Reconstruct the authoritative revision-2 context from registered identity, instantiate a fresh revision-2 public episode, apply each validated intent in order, then compare the **entire public state** with the source in round-trip tests, including revision, construction, histories and provenance.

| Envelope and definition | Result |
|---|---|
| v9 + comparison revision 1 + original three intent types | Accept under unchanged historical validation and results. |
| v9 + revision 2, or v9 + new helper intent | Refuse; never migrate or reinterpret. |
| v10 + comparison revision 2 + exact authoritative context and valid chronological intents | Accept and reconstruct public revision-2 state. |
| v10 + revision 1, another definition, wrong identity/context, unknown/extra keys, malformed wire or invalid phase/order | Refuse atomically; no fallback to v9. |
| v1–v8 + either comparison revision | Refuse under existing comparison-version boundaries. |

Both revisions retain their own registered identity/context and cue behavior; v9 historical full-state oracles stay unchanged. V10's schema literal is `fractionflow.episode-replay/v10`; the serializer remains unimplemented until this map is approved.

**Last requested cue.** Select the most recent `comparison-help-request` in the public assistance history, considering reasoning and notation together. If it is reasoning, project only the revision-2 reasoning cue (nonnumeric for close pairs); if notation, project only notation. Earlier requests remain in history/provenance but do not mask a newer request. Construction-help requests do not replace the last comparison reasoning/notation selection. This corrects the isolated checkpoint projection's current any-reasoning search during approved integration; no source correction is made in this documents-only clarification.
